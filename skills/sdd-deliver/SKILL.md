# Deliver — one change, from the dispatch gate to a ready pull request

> The plugin root is the folder that holds this skill's `skills/` folder (`${CLAUDE_PLUGIN_ROOT}` on Claude Code): take it from this file's own path, `\` turned into `/`, and never search the disk for it. `sdd-pr` below is `python3 <plugin root>/tools/sdd-pr.py`.

The procedure and its parameters come from the descriptor and this file, never from session memory. Run as the orchestrator on the strongest model available; **one change per session**: when this session already carries another pull request's work, say so first and recommend a fresh session, since the findings file and the delivery notes hold the state. `--lane` overrides step 1.

## Steps

0. **Read `docs/.sdd.yaml`:** `profile`, `paths.*`, `forge`, the build targets, the whole `agents:` block. No descriptor, or no `agents:` block: route to `/sdd-scaffold` and stop.
1. **Decide the lane — formal profile only.** The maintainer's lane is final (`--lane`, or named in words): never raise it; a concern is one line in the notes. Otherwise full or maintenance (methodology §12): does the change add an obligation or widen a contract? A correction of a sentence to the behaviour the change fixes is maintenance. Record it, and step 2's result, in the delivery notes, `<git-common-dir>/sdd/deliver/<branch-slug>.md`, which every worktree sees: it drives the later steps and the PR body's `Lane:` line.
2. **The dispatch gate.** Formal: methodology §9's five preconditions on the full lane; on maintenance, step 1's "no" and known verification commands. Informative: §9's two, with the constitution sentences the task touches quoted into the briefs. An unmet check stops the dispatch, named; route a missing `REQ`/`SPEC §`/`ADR` for a **new capability** to `/sdd-specify`. A maintainer's instruction that contradicts a sentence is no unmet check: it is the brief's `Decided` line, and the sentence is amended in this branch (methodology §7). Nothing else blocks the start.
3. **Branch; plan if the host plans.** Create or check out the feature branch. A plan (a planning skill's, a file under `.sdd/`, or a committed one marked `kind: plan`) is the orchestrator's own; given one, quote each task verbatim into its brief, never retyped or narrowed. On the maintenance lane and the informative profile a task list in the session is enough. Read `docs/backlog.md` when it exists: an item whose path a task's `Files` touch goes into that task's `Finding`, a lead to verify first ([review.md § The backlog](../../references/review.md#the-backlog)).
4. **Dispatch** one `sdd-implementer` per task, its brief begun with `sdd-pr brief --task "<task>"` and every field it leaves open filled (`Clauses`: only the sentences this task satisfies or changes, quoted; `Decided` when the maintainer's instruction contradicts one; `Reproduce` for a bug fix; `Code map`: what was already read for it), about 4k characters, the plan's narrative left out. Model per dispatch: `agents.worker_model` (none for `inherit`), or `agents.mechanical_worker_model`, when it names one, for a mechanical task with nothing to decide (a version bump, a wording fix, a test pin); never cheaper otherwise. Group small tasks into one. The sentences a task changes in `docs/`, the README and comments go in that task's `Files`, to the worker, in `/sdd-specify`'s form (a keyword only for what a caller relies on, a citation rather than a restatement); a map row or a test row may be edited in-session. **Sequential by default**, on the branch, in this worktree. A parallel wave, up to `agents.max_parallel_workers`, needs independent tasks (disjoint `Files`, no unit importing another's, none needing another's commit), each long enough to outlast a worker's start-up; with commit hooks that stash the tree (pre-commit, lint-staged), only under `worktree_per_worker`. The wave shares this worktree and the branch: each worker commits only its own files and verifies only its own unit; no host worktree isolation. `agents.worktree_per_worker: true` instead gives each parallel worker `<branch>--<task>` in its own worktree (`git worktree add -b`), briefed with `sdd-pr --root <that worktree> brief`, merged as step 7 says before the next wave. Notes: each task's `Files`, the split and why, each gate verdict. While workers run, the spec and their files hold still: an amendment waits for the wave's end, and a growing scope is a question to the maintainer.
5. **Gate each task** only per `agents.task_review` (default `off`: the first review pass is the gate; `lane`: on for the full lane and the informative profile). When on, the gate dispatches `agents.reviewers` (in map form, those whose patterns match the task's `Files`; none matching is unconfigured) with [templates/task-review.md](../../references/templates/task-review.md) filled for the task; a small, mechanical task's review may take a cheaper model. Its critical and important findings go to a new `sdd-implementer` dispatch for the task, its brief's `Finding` field carrying them, never back to the finished worker by message (a resumed worker re-reads its whole context every turn) and never to the findings file; a suggestion-only verdict opens no dispatch. An empty `agents.reviewers` with the gate on is unconfigured, not clean: say so and ask before continuing.
6. **Account for completion.** A worker that died is re-dispatched with its partial edits named in the brief, or the gap is named. When a parallel wave ends, each commit since it began (`git log --name-only <wave base>..HEAD`) touches one task's `Files`, each worker's reported files sit in its own list, and `git status` is clean; otherwise resolve it in-session before the next wave. Triage each worker's en-route findings: a sentence and the code that disagree is a defect in whichever side is wrong — the maintainer's instruction decides, else a sentence this branch wrote is corrected here and a merged one is fixed in the code, said once in the notes (methodology §6, §7). A defect in a file a task changed is fixed here, as a task; an out-of-scope defect with a small fix too; a larger one is settled as [review.md § Severity](../../references/review.md#severity) says, then `sdd-pr add <severity> … --outside` with that evidence; a lead that meets § Severity's bar, `sdd-pr add suggestion <path[:line]> "<sentence>" --by <worker>`; the rest is dropped. A task is done when its verification ran and its output was read.
7. **Gate, then the first review pass.** Worker branches, if any: merge each in dependency order after a trial merge in a throwaway worktree, then `git worktree remove`, `git worktree prune` and `git branch -d` each (`sdd-pr status` names any left). Run the generator once and commit what it wrote. Run the full gate — `<build_entrypoint> <ci_target>` (output to `.sdd/gate-<short head>.log`) and `<build_entrypoint> <spec_check_target>` — on the integrated branch and read the output. First **reconcile the documents**: every sentence in `docs/`, the README and the code's comments that describes what the change altered is brought up to date in this branch, a binding sentence or the constitution in `/sdd-specify`'s form, no keyword added for internals (methodology §4). Then run `/sdd-review --lane <lane>` (no `--lane` on the informative profile; [review.md § Passes](../../references/review.md#passes)), and work its open lines and its document fixes with `/sdd-triage`.
8. **Push, and open the pull request** with the repository's forge CLI, ready for review (a draft only when the maintainer asked for one); the body follows `docs/development-process.md` § The PR body (one sentence of Summary until close-out), or, when that section is missing, the repository's PR template, which the hand-back names. Then `sdd-pr post` mirrors anything still open.
9. **The maintainer's review.** Stop and wait; never merge, or mark a draft ready, on the orchestrator's own judgement. A conversation comment is an instruction; work the review with `/sdd-triage`.
10. **Close out** with `/sdd-close` once the maintainer's review is worked; after the merge, it runs again to clean up.

**Resuming.** Resume with the PR number, passed as `--pr N` to every `sdd-pr` call, or on the branch before a pull request exists: the delivery notes, `sdd-pr status` (which lists worker branches not yet integrated), the findings file and the PR body are the state; a resume re-checks step 2 before it dispatches again. Two sessions on one branch take turns on one checkout. Re-enter at the first step not yet done.

## Guardrails

- **The orchestrator writes no product code, except a task that cannot be made self-contained, named in the PR body.**
- **Workers never spawn workers.**
- **Ask the maintainer in plain words: the decision, the options, a recommendation.**
- **Fan-out through the host's Workflow tool (Claude Code only) is explicit opt-in: ask first.**
- **Never hand-edit a generated block.**

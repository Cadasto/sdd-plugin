# Deliver — one change, from the dispatch gate to a ready pull request

> The plugin root is the folder that holds this skill's `skills/` folder (`${CLAUDE_PLUGIN_ROOT}` on Claude Code): take it from this file's own path, `\` turned into `/`, and never search the disk for it; `references/…` and `tools/…` resolve from it. `sdd-pr` below is `python3 <plugin root>/tools/sdd-pr.py`.

The procedure and its parameters come from the descriptor and this file, never from session memory. Run as the orchestrator on the strongest model available. `--lane` overrides step 1. `--close-out` is now `/sdd-close`: follow that skill, with the same PR number.

## Steps

0. **Read `docs/.sdd.yaml`:** `profile`, `paths.*`, `forge`, the build targets, the whole `agents:` block. No descriptor, or no `agents:` block: route to `/sdd-scaffold` and stop.
1. **Decide the lane — formal profile only.** Full or maintenance (methodology §12, or `--lane`): does the change alter a normative statement? Record it, and step 2's result, in the delivery notes, `<git-common-dir>/sdd/deliver/<branch-slug>.md`, which every worktree sees: it drives the later steps and the PR body's `Lane:` line.
2. **The dispatch gate.** Formal: methodology §9's five preconditions on the full lane; on maintenance, step 1's "no" and known verification commands. Informative: §9's two, with the constitution sentences the task touches quoted into the briefs. An unmet check stops the dispatch, named; route a missing `REQ`/`SPEC §`/`ADR` to `/sdd-specify`. Nothing else blocks the start.
3. **Branch; plan if the host plans.** Create or check out the feature branch. A plan (a planning skill's, a file under `.sdd/`, or a committed one marked `kind: plan`) is the orchestrator's own; given one, quote each task verbatim into its brief, never retyped or narrowed. On the maintenance lane and the informative profile a task list in the session is enough. Read `docs/backlog.md` when it exists: an item whose path a task's `Files` touch goes into that task's `Finding`, a lead to verify first (`references/review.md` § The backlog).
4. **Dispatch** one `sdd-implementer` per task, every field of `references/templates/brief.md` filled (`Clauses` quoted, `Reproduce` for a bug fix, `agents.worker_skills`, the code index from `docs/ai-workflow.md` § Orchestration), `agents.worker_model` as the per-dispatch model override (none for `inherit`), never a cheaper one. Group small tasks (a test pin, a wording fix) into one; a sentence, a map row or a test row is edited in-session, a specification, requirement or ADR sentence in `/sdd-specify`'s form (a keyword on a binding sentence, a citation rather than a restatement). **Sequential by default**, on the branch, in this worktree. A parallel wave, up to `agents.max_parallel_workers`, needs independent tasks (disjoint `Files`, no unit importing another's, none needing another's commit), each long enough to outlast a worker's start-up; with commit hooks that stash the tree (pre-commit, lint-staged), only under `worktree_per_worker`. The wave shares this worktree and the branch: each worker commits only its own files and verifies only its own unit; no host worktree isolation. `agents.worktree_per_worker: true` instead gives each parallel worker `<branch>--<task>` in its own worktree (`git worktree add -b`), merged as step 7 says before the next wave. Notes: each task's `Files`, the split and why, each gate verdict. While workers run, the spec and their files hold still: an amendment waits for the wave's end, and a growing scope is a question to the maintainer.
5. **Gate each task** per `agents.task_review` (`lane`: on for the full lane and the informative profile, off for maintenance). The gate dispatches `agents.reviewers` (in map form, those whose patterns match the task's `Files`; none matching is unconfigured) with `references/templates/task-review.md` filled for the task; a small, mechanical task's review may take a cheaper model. Its findings go to a new `sdd-implementer` dispatch for the task, its brief's `Finding` field carrying them, never back to the finished worker by message (a resumed worker re-reads its whole context every turn) and never to the findings file; the delivery notes count them for the PR body's Verification. An empty `agents.reviewers` with the gate on is unconfigured, not clean: say so and ask before continuing.
6. **Account for completion.** A worker that died is re-dispatched with its partial edits named in the brief, or the gap is named. When a parallel wave ends, each commit since it began (`git log --name-only <wave base>..HEAD`) touches one task's `Files`, each worker's reported files sit in its own list, and `git status` is clean; otherwise resolve it in-session before the next wave. Triage each worker's en-route findings: a sentence the code does not meet is a defect in the code, fixed in the code (narrowing the sentence is the maintainer's call); in scope, a task; an out-of-scope defect, settled as `references/review.md` § Severity says, then `sdd-pr add <severity> … --outside` with that evidence; an out-of-scope lead (`references/review.md` § Severity), `sdd-pr add suggestion <path[:line]> "<sentence>" --by <worker>`. A task is done when its verification ran and its output was read.
7. **Gate, then the first review pass.** Worker branches, if any: merge each in dependency order after a trial merge in a throwaway worktree, then `git worktree remove`, `git worktree prune` and `git branch -d` each (`sdd-pr status` names any left). Run the generator once and commit what it wrote. Run the full gate — `<build_entrypoint> <ci_target>` (output to `.sdd/gate-<short head>.log`) and `<build_entrypoint> <spec_check_target>` — on the integrated branch and read the output. First **reconcile the documents**: every sentence in `docs/`, the README and the code's comments that describes what the change altered is brought up to date in this branch, a binding sentence or the constitution only through `/sdd-specify`. Then run `/sdd-review --lane <lane>` (no `--lane` on the informative profile; `references/review.md` § Passes) and fix its open lines with `/sdd-triage`.
8. **Push, and open the pull request** with the repository's forge CLI, ready for review (a draft only when the maintainer asked for one); the body follows `docs/development-process.md` § The PR body (one sentence of Summary until close-out), or, when that section is missing, the repository's PR template, which the hand-back names. Then `sdd-pr post` mirrors anything still open.
9. **The maintainer's review.** Stop and wait; never merge, or mark a draft ready, on the orchestrator's own judgement. A conversation comment is an instruction; work the review with `/sdd-triage`.
10. **Close out** with `/sdd-close` once the maintainer's review is worked; after the merge, it runs again to clean up.

**Resuming.** Resume with the PR number, passed as `--pr N` to every `sdd-pr` call, or on the branch before a pull request exists: the delivery notes, `sdd-pr status` (which lists worker branches not yet integrated), the findings file and the PR body are the state; a resume re-checks step 2 before it dispatches again. Two sessions on one branch take turns on one checkout. Re-enter at the first step not yet done.

## Guardrails

- **The orchestrator writes no product code, except a task that cannot be made self-contained, named in the PR body.**
- **Workers never spawn workers.**
- **Ask the maintainer in plain words: the decision, the options, a recommendation.**
- **Fan-out through the host's Workflow tool (Claude Code only) is explicit opt-in: ask first.**
- **Never hand-edit a generated block.**

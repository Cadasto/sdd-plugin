# Testing and validation

This page is for contributors changing the plugin: what each validator checks, and how to exercise every component by hand before a release. The repository is pure content (JSON manifests and Markdown components) with no build step and no package manager. Testing means validating structure, then installing locally and exercising the components.

## Validation

- **Manifest and component validation:** `./scripts/validate.sh` (CI runs the underlying `python3 scripts/validate.py` directly on every PR). It checks both `plugin.json` manifests, dual-host parity (name, version, description, author, license, repository, and keywords agree), declared component paths, kebab-case names, hook-config JSON, and SKILL.md, agent, and command frontmatter (including `name` == directory/filename, and that agents declare a grant, `tools:` or `disallowedTools:`, never `allowed-tools:`). It also checks that every relative link and `.md` fragment resolves, that retired vocabulary hasn't crept back in, that every skill and the review and delivery path stay within their word budgets (`WORD_BUDGETS`), that no skill, agent, template or hook names a forge CLI, and that both tools' `__version__`, the template's pinned `check.version`, and both manifests' `version` agree. If Python 3 isn't installed, the wrapper prints a warning and skips (exit 0) rather than failing; install `python3` for the full local check, or rely on `claude plugin validate .` and CI. CI pins Python so the deep check always runs there.
- **Official validator:** `claude plugin validate .` checks the manifest and component structure (no extra dependencies).
- **Tool tests:** `python3 -m unittest discover -s tools/tests -v` runs the unit tests of the vendored gate and of `sdd-pr` (whose forge calls are faked; no test touches the network); `python3 tools/sdd-check.py selftest` runs it against the fixtures it carries and reports pass or fail per rule, with one positive and one negative case each. CI runs both after the validator.
- **Hook tests:** `bash scripts/hooks-test.sh` runs the three hook scripts against scratch git repositories (the session-start orientation, the edit reminder, and the one-shot stop nudge on both hosts' payloads) and needs only bash and git. `./scripts/validate.sh` runs it even when Python is absent, and CI runs it last.
- **CI matrix:** CI runs every step above on Python 3.9, the tool's stated floor, and on current 3.x, so a construct newer than 3.9 fails the build.
- **Structural review:** run the `plugin-dev:plugin-validator` agent after creating or modifying components.
- **Skill quality review:** run the `plugin-dev:skill-reviewer` agent for description-triggering quality, progressive disclosure, and content structure.
- **Token cost:** `claude plugin details sdd` shows the inventory and projected token cost; keep skill and command metadata lean.

## Local triggering tests

Install from your working copy (see [install.md](install.md)), then exercise each component. The most thorough test is to **dogfood the plugin on a throwaway repo**:

- **Session-start hook:** open a repo containing `docs/.sdd.yaml`; the SDD context line names the profile, `› sdd plugin <version>` follows on Claude Code, and a `› findings:` line appears when the branch has a findings file (the scaffold pointer shows in a repo with `docs/` but no SDD structure).
- **`spec-driven-development` router:** ask "what is SDD?" or "should I write a spec or a requirement?"; it should explain and route, not perform an artefact action.
- **`/sdd-scaffold`:** in an empty repo, run it once per profile and confirm the `docs/` tree (or, on informative, `docs/architecture.md` and no map), `docs/.sdd.yaml`, `AGENTS.md`, the PR template and the `.sdd/` ignore line appear; run it again and confirm it is idempotent (fills gaps, doesn't clobber).
- **`/sdd-specify`:** capture a REQ, write a SPEC §, record an ADR; confirm identifiers are assigned without collision, the traceability entry is written, and a doc-kind boundary violation (for example a file path in a requirement) is refused or flagged.
- **`/sdd-deliver`:** on a REQ whose spec is written, confirm it refuses to dispatch when a precondition is unmet (no spec, no acceptance criteria), commits no plan, runs the first review pass on the branch before any pull request exists, and opens a **draft** PR whose body follows `docs/development-process.md` § The PR body. On the informative profile, confirm it starts without a `REQ` and reconciles the affected documents.
- **`/sdd-trace`:** with a deliberately broken `canonical` link, confirm the drift is reported (report-only, no edits).
- **`/sdd-review`:** on a branch with no pull request, confirm `.sdd/findings/<branch>.md` appears with a `Reviewed` line; run it again with no new commit and confirm `range: empty` stops it; after a code change, confirm only the reviewers for the changed file kinds are dispatched.
- **`/sdd-review --panel`:** confirm it prints one prompt block per `review_panel` entry for the lane and posts nothing.
- **Findings file across hosts:** have Cursor append two lines to the same file from the panel prompt; confirm `/sdd-triage` in Claude sees and works them.
- **`sdd-pr`, read-only on each forge you have:** `status` and `scope` on a branch with and without a pull request; `pull` on a scratch copy of the file. With `forge: none`, confirm `pull`, `post` and `resolve` exit 2.
- **The mirror, on a scratch pull request:** `post` (one review, one inline thread per critical or important line; a line outside the diff marked `unanchored`), an inline comment of your own brought in by `pull` as important, `/sdd-triage` fixing one and declining one, `resolve` answering and closing both threads, and `status` ending in `Mergeable: yes`.
- **`/sdd-deliver --close-out`:** confirm the record's `implementation: shipped` is set in `traceability.yaml`, that a `SPEC §` stays `draft` unless you confirm promotion, and that nothing is pushed before the full gate has run green.
- **Reviewer agents:** run `/sdd-trace --audit` (`sdd-traceability-auditor`), a document review (`sdd-doc-reviewer`), and a conformance check (`sdd-spec-conformance-reviewer`); confirm each returns findings-file lines with evidence and none edits files or spawns sub-agents.
- **`sdd-implementer`:** dispatch it with a one-task brief; confirm it stays inside the files the brief names, reports a `Can-fail proof` and an `En-route findings` section, and spawns no sub-agents.
- **`spec-edit-reminder` hook** (Claude Code): edit a file under `docs/specifications/`; confirm the one-line reminder prints; on the informative profile, confirm only a constitution edit prints one.
- **`session-stop` hook:** leave uncommitted changes with no commit in the session and stop; confirm the one-shot nudge fires (Claude Code: `Stop` exits 2 with the reason on stderr; Cursor: a `stop` followup message) and that a second stop in the same session passes silently. Confirm a session that made a commit is never nudged, and that `hooks.stop_nudge: false` in `docs/.sdd.yaml` opts the repository out.
- **`sdd-check generate --verify`:** after adding or amending a traceability record, run it; confirm it reports what would change in the generated blocks and the requirement frontmatter without writing anything, then run `sdd-check generate` (no flag) and confirm the reported changes land.
- **Cursor rule:** in Cursor, open a file under `docs/` and confirm `sdd-context.mdc` attaches.
- **Cursor smoke:** install the branch as a Cursor plugin; dispatch `sdd-implementer` with a one-task brief and confirm it spawns no subagent (a stated contract there, not a grant); run `/sdd-review` on a branch and confirm the findings file appears, and that `sdd-pr pull` fails loud rather than silently when the forge CLI is missing. Open the workspace in a new session and end one with uncommitted changes: confirm `sessionStart` prints its context and `stop` nudges once. That is the one live check the Cursor hook wiring still needs ([install.md](install.md#cursor)).

After editing content, reinstall (or restart the session) to pick up changes.
